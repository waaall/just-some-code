# 乱码分析报告


## 乱码来源和分类

### 乱码分类

乱码有两种情况: 我称之为一型和二型。
    1. 原始编码可能为encoding_init(gbk或者gb2312), 被错误的解码decoding(比如utf8或者Latin-1)就会乱码;
       这时候检测encoding然后统一重编码为utf8(文件没有被错误编码, 也就是encoding_init==encoding_end); 再按照utf8 decoding(这都是默认)
    2. 原始编码可能为encoding_init(gbk或者gb2312), 被错误地用encoding_mid(Latin-1或Windows-1252解码), 然后重编码为当前的encoding_end(可能是utf8或者是gb2312)

### 二型乱码过程
乱码过程:
1. 原始状态: 原始文本用A用GB2312编码 → 得到字节序列x
2. 错误解码: 用UTF-8解码字节序列x → 得到乱码文本B
3. 错误重编码: 将乱码文本B用GB2312编码 → 得到字节序列y

## 逆向处理过程

假设我们知道每一步使用的编码
- 原始编码: gb2312
- 错误解码: utf-8
- 错误重编码: gb2312

1. 用错误重编码的编码(gb2312)解码字节序列y→ 得到乱码文本B
text_B = bytes_c.decode('gb2312')

2. 用错误解码的编码(utf-8)编码乱码文本B → 得到原始字节序列x
bytes_fake_x = text_B.encode('utf-8')
(注意, 这一步可能是不可逆的, 由于x不兼容这个编码方式, 可能x没有到B的一对一映射, 所以B可能编码不出原有的x)

3. 用原始编码(gb2312)解码字节序列x → 得到原始文本A
original_text = bytes_fake_x.decode('gb2312')



### 逆向处理的挑战

然而, 在实际操作中, 面临两个问题:

1. 信息丢失
当使用错误的编码解码时, 可能会发生不可逆的信息丢失:
- 某些字节序列在错误编码中可能无法表示, 被替换为占位符(如�)
- 某些字符在转换过程中可能被映射到不同的字符

2. 多重编码的可能性
实际场景中可能涉及更多层次的编码错误, 而不仅仅是两层。

1. 【编码检测】
   - 系统级检测: 使用 file --mime-encoding 命令
   - 乱码分析: 通过 charset_normalizer 分析乱码模式
   - 优先级管理: 三级编码优先级调整

2. 【批量修复生成】
   - 一型修复: 为每种编码生成单独的修复文件
   - 二型修复: 生成所有可能的编码链组合修复文件
   - 质量评估: 自动评估修复质量(中文字符数、乱码检测)

注: 对于二型乱码，英语字符修复概率很大，但是中文字符被修复概率很小（因为被重编码的编码类型没有对应的符号就会被映射成同样的二进制数据，但是信息丢失，即上文中的《逆向处理的挑战》第一条）
